Visión general y arquitectura

Agent Hub es una aplicación Electron que actúa como panel de control para agentes de Claude Code. Todo el estado persiste en disco — no hay base de datos. El proceso principal levanta un servidor Express en localhost:3737 que sirve tanto los assets del renderer como la API REST. El renderer está dividido en módulos JS independientes cargados desde src/renderer/js/.

Rendererindex.html · JS modules
Context Bridgewindow.api (IPC)
Main Processmain.js · Electron
Express :3737API REST
Discoagents/ · config.json
Runtime
Electron 29 + Node.js embebido. Portable — sin instalador.
Servidor
Express 4 en 127.0.0.1:3737. Solo accesible localmente.
Persistencia
Ficheros .md con frontmatter YAML. config.json para metadatos.

Módulos principales

main.js — Ciclo de vida de Electron, ventana, IPC handlers, tray, auto-updater.
Single-instance lock. Inicia Express, crea ventana y tray, configura electron-updater.
server.js — Servidor Express embebido. Define todos los endpoints de la API REST.
Sirve el renderer como archivos estáticos. Catch-all redirige a index.html.
agents.js — Parse, serialización, CRUD, hashes SHA-256, seeding de defaults, mirror a ~/.claude/agents/.
parseAgentFromString() también se usa para importación de agentes externos por URL.
projects.js — Crear, importar, actualizar, eliminar proyectos. Sync de agentes. Lectura/escritura de CLAUDE.md.
syncProject() copia agentes aplicables y actualiza agentHashes en config.json.
ai.js — Abstracción sobre los tres proveedores. getProviderStatus(), generateAgentPrompt(), getSuggestions().
Las sugerencias se cachean en cache/suggestions.json por clave de nivel.
config.js — readConfig(), writeConfig(), bootstrapDirectories(), APP_DIR, getAgentDir().
APP_DIR es el directorio del .exe en producción (PORTABLE_EXECUTABLE_DIR) o la raíz del proyecto en dev.
preload.js — Context bridge. Expone window.api al renderer con contextIsolation habilitado.
nodeIntegration: false. El renderer no tiene acceso directo a Node.js.

Mirror de globales a ~/.claude/agents/

Cada vez que se crea, actualiza o elimina un agente de nivel global, syncGlobalAgentsToClaudeDir() copia todos los ficheros de agents/global/ a ~/.claude/agents/. Esto hace que los agentes globales estén disponibles en cualquier proyecto desde la CLI de Claude Code sin necesidad de sync manual.

Nivel 3 — Tecnología

04

Formato de agentes

Cada agente es un fichero .md con un bloque de frontmatter YAML delimitado por ---. Agent Hub siempre serializa el campo model con el ID completo de Claude. La UI muestra el alias corto.

Estructura del fichero

--- name: unity-dev description: Experto en Unity, C# y arquitectura de GameObjects model: claude-sonnet-4-20250514 tools: - Bash - Read - Write - Grep --- Eres un experto en Unity 2023 LTS. Dominas MonoBehaviour, ScriptableObjects, prefabs y URP...

Campos del frontmatter

name — identificador único dentro del nivel. Solo minúsculas, guiones. Coincide con el nombre del fichero.
description — texto corto. Claude Code lo usa para la delegación automática de tareas.
model — ID completo del modelo Claude. CDM acepta aliases cortos en la UI y los resuelve al serializar.
tools — lista YAML de herramientas habilitadas para el agente.

Aliases de modelo

haiku
claude-haiku-4-5-20251001
sonnet
claude-sonnet-4-20250514
opus
claude-opus-4-20250514

Herramientas disponibles

Bash Read Write Edit MultiEdit Grep WebFetch WebSearch TodoRead TodoWrite

parseAgentFromString(content, fallbackName)

Función exportada de agents.js que parsea un string de texto en lugar de un fichero. Acepta tanto la sintaxis de lista YAML como la sintaxis inline para el campo tools. Se usa para la importación de agentes externos por URL antes de que se guarden en disco.

// Retorna: { name: string, description: string, model: string, // alias corto tools: string[], system: string, }

Agentes incluidos por defecto (nivel global)

code-reviewer — Revisa código buscando bugs, antipatrones y mejoras. Modelo: sonnet
git-helper — Commits, ramas y resolución de conflictos. Modelo: haiku
test-writer — Genera tests unitarios e integración. Modelo: sonnet
doc-writer — Documentación técnica en Markdown. Modelo: sonnet
refactor-agent — Refactoriza código manteniendo funcionalidad. Modelo: sonnet
debugger — Diagnóstico y corrección de errores. Modelo: sonnet
Migración automática de formato
migrateAgentFiles() se ejecuta en cada arranque. Si detecta agentes en formato antiguo (model como alias corto, tools inline), los reescribe al formato canónico. Los agentes seeded también se actualizan si están en formato antiguo.
05

Sistema de hashes y sync

Agent Hub usa hashes SHA-256 para detectar si los agentes copiados en un proyecto están desactualizados respecto a la versión maestra en el manager. El hash se calcula sobre el contenido serializado del agente (no sobre el fichero en disco directamente) para evitar diferencias de CRLF/LF.

Flujo de sync

getApplicableAgentsglobal + section + tech
hashAgent()SHA-256 del serializado
Compararhash vs config.agentHashes
Copiarsi hash difiere o no existe
Guardarnuevo hash en config.json

Estado de cada agente en un proyecto

ok
El hash del fichero copiado coincide con el maestro. No hay cambios pendientes.
outdated
El agente maestro cambió desde la última sync. El proyecto muestra badge ↑N.
new
Agente aplicable que aún no existe en el proyecto (nunca fue copiado).
local
Agente de nivel 4 (propio del proyecto). CDM no lo toca durante el sync.

Endpoints de sync

POST /api/projects/:id/sync → sync un proyecto individual POST /api/sync-all → sync todos los proyectos GET /api/projects/:id/sync-status → estado actual sin modificar nada

hashAgent() vs hashFile()

hashAgent(agent) serializa el objeto agente a string y hace SHA-256. hashFile(filePath) lee el fichero y hace SHA-256 del contenido crudo. CDM usa hashAgent() para calcular el hash de la versión maestra y lo guarda en config.json. Para comparar, calcula el hash del agente maestro y lo compara con el almacenado.

07

Proveedores de IA

Agent Hub abstrae tres proveedores distintos detrás de una interfaz común en ai.js. El proveedor activo se guarda en config.aiProvider.

Proveedor: cli
Claude CLI — suscripción claude.ai
Llama a la CLI de Claude Code instalada en el sistema. Sin coste adicional. Requiere claude en PATH. Agent Hub detecta la CLI con where claude (Windows) o which claude. El token de acceso del usuario lo gestiona la propia CLI.
Proveedor: api
API key de Anthropic
Usa el SDK oficial @anthropic-ai/sdk. Requiere una API key de console.anthropic.com almacenada en config.apiKey. Tiene coste por token.
Proveedor: github
GitHub Copilot Models API
Oculto en la UI de ajustes (hidden en el DOM) pero funcional. Requiere un Personal Access Token con permiso models:read y un modelo seleccionado (gpt-4o-mini, gpt-4o u o1-mini). Token en config.githubToken, modelo en config.githubModel. Disponible en el wizard.

Funciones exportadas de ai.js

getProviderStatus() → { provider, ready, ... } — comprueba si el proveedor activo está operativo generateAgentPrompt({ description, name, level, categoryId, techId, tools, language, existingAgents }) → string — system prompt generado getSuggestions({ level, categoryId, techId, existingAgents }, force) → AgentSuggestion[] — lee del cache o genera nuevo si force=true clearSuggestionsCache() → void — elimina cache/suggestions.json

Cache de sugerencias

Las sugerencias se cachean en cache/suggestions.json con clave compuesta {level}:{categoryId}:{techId}. Incluyen timestamp y lista de agentes sugeridos con nombre, descripción y herramientas propuestas. La UI ofrece el botón "Sugerir más" que llama a POST /api/ai/suggestions/refresh para forzar regeneración. Las sugerencias nunca repiten agentes que ya existen en ese nivel.

08

Auto-update

Agent Hub usa electron-updater v6 con GitHub Releases como provider. El mecanismo es opt-in: la descarga no empieza hasta que el usuario pulsa el botón en el banner.

Configuración (app-update.yml)

provider: github owner: adanoliva repo: cdm private: true updaterCacheDirName: agent-hub-updater

Opciones del auto-updater

autoUpdater.token = 'ghp_...' // token read-only para repo privado autoUpdater.autoDownload = false autoUpdater.autoInstallOnAppQuit = false autoUpdater.logger = null

Ciclo de actualización

Arranque +8scheckForUpdates()
update-availableBanner en UI
Usuario pulsadownloadUpdate()
update-downloadedBotón "Reiniciar"
quitAndInstallReemplaza .exe

IPC del updater

update:check → invoca autoUpdater.checkForUpdates(). Usado por el botón manual de ajustes.
update:download → invoca autoUpdater.downloadUpdate().
update:install → invoca autoUpdater.quitAndInstall(false, true).
Solo en producción
setupAutoUpdater() retorna inmediatamente si isDev === true. El auto-update no se ejecuta con npm run dev.

Banner de actualización (renderer)

El banner es un div fijo en la esquina inferior derecha (position:fixed; bottom:28px; right:16px), oculto por defecto. Cuando llega el evento update-available via window.api.onUpdateAvailable(), el banner se muestra con el número de versión y el botón de descarga. Al completarse la descarga (update-ready), el botón cambia a "Reiniciar ahora".

Importación de agentes externos

Desde Ajustes → Agentes externos se puede importar cualquier fichero .md con frontmatter publicado en una URL. El flujo completo es:

URLAjustes → Agentes externos
POST /api/agents/import-urlDescarga + parse
Preview modalRevisión editable
Elige destinoGlobal/Sección/Tech
POST /api/agentsGuarda en disco

Endpoint POST /api/agents/import-url

El servidor descarga el contenido de la URL usando los módulos http/https de Node.js (sigue redirecciones 3xx). Pasa el string resultante a parseAgentFromString(content, fallbackName) donde fallbackName se extrae del último segmento de la URL sin extensión. Retorna el objeto agent sin guardarlo en disco — el guardado lo hace el renderer en un segundo paso con POST /api/agents.

Preview editable

El modal de revisión muestra todos los campos del agente parseado: nombre, descripción, modelo, herramientas (checkboxes) y system prompt (textarea). El usuario puede editar cualquier campo antes de guardar. El selector de destino permite elegir entre Global, cualquier Sección o cualquier Tecnología existente en la configuración.

Arquitectura del renderer

El renderer sigue el principio de responsabilidad única: src/renderer/index.html es solo el shell HTML, src/renderer/styles.css contiene todo el CSS, y src/renderer/js/ contiene los módulos JS (utils, state, api, toast, modal, category-helpers, view-manager, projects-view, agents-view, settings-view, wizard, update, init). Express sirve el directorio src/renderer/ como estáticos.

El estado global de la UI vive en el objeto S. Todas las peticiones a la API se hacen mediante fetch() a http://localhost:3737/api/... a través de la función req(method, endpoint, body).

Build y release

Scripts npm

npm run dev — Arranca Electron en modo desarrollo (NODE_ENV=development). Las DevTools se abren automáticamente.
npm run build — Ejecuta el prebuild (genera icono), compila con electron-builder --win portable y el postbuild. Genera dist/agent-hub.exe.
npm run build:dir — Compila sin empaquetar en asar. Útil para depurar la estructura de archivos del build.
npm run release — electron-builder --win portable --publish always. Sube el .exe y el latest.yml a GitHub Releases. Requiere GH_TOKEN en el entorno.

electron-builder.yml — puntos clave

appId: com.adanoliva.agent-hub publish: provider: github owner: adanoliva repo: cdm private: true portable: artifactName: agent-hub.exe extraResources: - from: assets/ → process.resourcesPath/assets/ - from: app-update.yml → incluido en el bundle para electron-updater asar: true compression: maximum

Artifacts generados por npm run release

agent-hub.exe
Ejecutable portable para el usuario final. Se sube a GitHub Releases como asset descargable.
latest.yml
Manifiesto de versión con SHA-512 del .exe. electron-updater lo consulta para detectar nuevas versiones.

Proceso de release paso a paso

# 1. Actualizar versión npm version patch # o minor / major # 2. Commitear y pushear git add package.json git commit -m "chore: bump v1.2.x" git push # 3. Publicar $env:GH_TOKEN = "ghp_..." npm run release # electron-builder crea el tag, sube .exe y latest.yml # Los usuarios con versiones anteriores ven el banner # de actualización en su próximo arranque.

APP_DIR en producción

En un portable de Electron, process.env.PORTABLE_EXECUTABLE_DIR apunta al directorio donde está el .exe. config.js lo usa como APP_DIR para que config.json, agents/ y cache/ vivan junto al ejecutable, haciendo la app completamente portable.
